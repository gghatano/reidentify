# 既定値の変更履歴

このパッケージは安全性評価ツールなので、**同じコードに同じデータを与えて過去と違う数値が出る**変更は、
それが意図的なものであっても記録に残す。ここはその記録である。

「壊れていたものを直した」変更はここには書かない。**意図的に既定を変えた**ものだけを書く。

---

## 1. `confidence` の既定を `"tie"` → `"margin"`（Issue #44）

**対象**: `match_greedy()`, `match_optimal()`, `reid_evaluate()`, `reid_per_anon()` の
`confidence` 引数、および `reid_confidence()` の `method` 引数。

**変更前**: `"tie"`（= `1 / 同点候補数`）
**変更後**: `"margin"`（= eccentricity `(2位のスコア − 1位のスコア) / sd(候補スコア)`）

### なぜ変えたか

#12 で「攻撃者は全件を当てにいかない。一部を高精度で特定する方が深刻」という前提を置いた。
それを測るのが `reid_evaluate()` の精度–再現率(PR)曲線である。

ところが `"tie"` は**連続スコアでは解像度がない**。最良候補が一意な記録はすべて 1 になるため、
連続スコアではほぼ全件が 1 に潰れ、PR 曲線の閾値が 1 点しか取れない。
1 点しか取れない PR 曲線は、全体成功率をもう一度書いているだけで、
「リスクの形」を見せるという指標本来の目的を果たさない。

`"margin"` は確率ではないが**順序**であり、閾値スイープが必要とするのは順序である。

### 何が変わり、何が変わらないか

**変わるもの** — `CONFIDENCE` 列と、それを閾値に使うすべて:

- `match_greedy()` / `match_optimal()` の `CONFIDENCE` 列
- `reid_evaluate()` の `precision_recall` 表と `per_record$CONFIDENCE`
- `min_confidence` の意味するスケール
- `reid_confidence()` の `CONFIDENCE` 列（`TIE_SIZE` / `MARGIN` / `SD_SCORE` /
  `ECCENTRICITY` はどちらの設定でも同じ値が入る）

**変わらないもの** — リスクそのもの:

- 割り当て結果（`RAW_ROW_NUMBER`）と `RESULT`
- `success_analytic` / `success_mean` / `success_sd` / `baseline` / `lift`
- `top_k` / `per_record$RISK` / `max_risk`

信頼度は記録を**並べ替える**だけで、リスクを変えない。これは
`test-confidence.R` と `test-evaluate.R` でアサートしてある。

リスクは同じで、見え方だけが変わった。

### 過去の数値を再現するには

`confidence = "tie"`（`reid_confidence()` では `method = "tie"`）を明示的に渡す。
`"tie"` は削除していない。

### 移行時に確認すべきこと

1. **`CONFIDENCE` をリテラルと比較しているコード** — `CONFIDENCE == 1` は
   `"tie"` では「最良候補が一意」を意味したが、`"margin"` では何も意味しない。
2. **`min_confidence` に定数を渡しているコード** — スケールが違う。次項を参照。
3. **過去に出した報告書との比較** — `success_analytic` などのリスク量は比較できる。
   PR 表と `CONFIDENCE` は比較できない。

### 併せて重要: eccentricity にはスケールの可搬性がない

これは既定を変えたこと自体より重要かもしれない。

eccentricity は**その記録自身の候補スコアの散らばり**に対する比なので、
数値の範囲はスコア表の性質で決まり、リスクの大きさでは決まらない。

| スコア表 | eccentricity の最大値 |
|---|---|
| 密な 150 人 2 属性の数値フィクスチャ | **0.45** |
| 疎なトランザクション的スコア（#23） | **4.86** |

一桁違う。しかも密な方は 98% が再識別された条件である。したがって:

- **閾値はデータセット間で使い回せない。** `min_confidence = 0.3` は、
  あるスコア表では上位 1 割を攻撃し、別のスコア表では全件を攻撃する。
- **Narayanan & Shmatikov の φ = 1.5 は移植できない。** 疎データ向けの値であり、
  密データでは全件を棄却して 0 を返す。
  「閾値が違うスケールだったので 0 件」と「本当に安全なので 0 件」は
  出力上区別がつかない（`docs/lessons-learned.md` §2）。
  `match_greedy()` / `match_optimal()` は全件棄却時に警告するが、
  それは最後の砦であって、閾値を選ぶ作業の代わりにはならない。
- **2 つの eccentricity を比べてよいのは同一スコア表の中だけ。**
  「A は 0.9 まで出たが B は 0.4 だから A の方が危険」は読み取れない。
  データセット間の比較には `reid_evaluate()` の `success_analytic` や
  `max_risk` を使う。これらは信頼度の選択に影響されない。

閾値は必ず実測分布から取る:

```r
stats::quantile(reid_confidence(scores, "margin")$CONFIDENCE, 0.9)
```

`"tie"` にはこの問題がない（`(0, 1]` の確率で、どこでも同じ意味を持つ）。
それが解像度をほぼ完全に失うことの代償である。

### テスト側の対応

既定変更で落ちたアサーションは **19 件（6 ファイル・10 テスト）**。
Issue #44 本文の見積もりは 3 箇所だったが、実測はその 6 倍以上だった。内訳:

| ファイル | 落ちたアサーション | 落ちたテスト |
|---|---|---|
| `test-layers.R` | 5 | 3 |
| `test-evaluate.R` | 7 | 1 |
| `test-confidence.R` | 3 | 2 |
| `test-generalize.R` | 2 | 2 |
| `test-assignment.R` | 1 | 1 |
| `test-setsim.R` | 1 | 1 |

見積もりが外れた理由は、`match_greedy()` の `CONFIDENCE` を
`1/k` としてアサートしている箇所が、信頼度そのものを扱うテストファイル以外
（集合類似度・一般化・レイヤ結合）にも散らばっていたため。
`docs/lessons-learned.md` §1「コードを読んだだけの指摘は、起票前に実行して確かめる」の
再現である。方針は次のとおり:

- **`1/k` の算術そのものを検証しているテスト**は `confidence = "tie"` を明示的に渡し、
  書かれたときの意図を保つ（`test-layers.R`, `test-assignment.R`,
  `test-generalize.R`, `test-setsim.R`, `test-evaluate.R` の tie 版）
- **既定そのものを検証していたテスト**は意図を反転させて書き直す
  （`test-confidence.R` の "match_greedy() defaults are unchanged by the new
  arguments" → "the confidence default is 'margin' (#44)"）
- **新しい既定の数値を固定する**テストを追加する
  （`test-evaluate.R` の "the default sweep ('margin', #44) refines the tie
  sweep rather than replacing it"）

`confidence = "tie"` を足しただけの箇所も、なぜ足したのかをコメントで残してある。
黙って引数が増えていると、次に読む人には「元からそう書かれていた」ようにしか見えないため。

## 検討したうえで維持した既定

数値は変わっていないので上の履歴には入らないが、判断が下りた記録として残す。

### `screen` は `"warn"` のまま（Issue #43）

**対象**: `score_multi()` と `score_by_knowledge()` の `screen` 引数。
**結論**: `"warn"`（検出して警告するが、動作は変えない）を維持。

`"none"`（検出しない）は #35 の目的そのものを潰す。無情報な軸を等重みで統合すると
単一属性より成功率が下がる（8 シード中 4 つ）という状態に黙って戻り、
利用者は「手がかりを増やしたのだから強い攻撃になったはず」と考えるので、
下がった数値を疑わない。`docs/lessons-learned.md` §2 の失敗様式そのものである。

`"drop"`（検出した軸を自動除外）は効果が実測されている
（静的属性のみを下回るシードが 4/8 → 0/8、等重み統合に対し 8/8 で改善、平均 +0.0969）が、
利用者が知らないうちに軸が消えるため「何を測ったのか」が入力次第で変わる。
安全性評価の結果を対外的に説明する場面で不利なので、既定にはしない。

**代わりに行ったこと**: 既定 `"warn"` により既存テストが出していた警告 8 件を、
`expect_warning()` で包んで意図を明示した（6 テスト・3 ファイル）。

| ファイル | テスト数 | 警告数 |
|---|---|---|
| `test-activity.R` | 1 | 1 |
| `test-knowledge.R` | 3 | 5 |
| `test-multiattr.R` | 2 | 2 |

8 件すべて真陽性である（定数列 `CONST`、一般化後に定数化した `ZIP`、
n=8 で順位 0.523 の列、2 行しかないフィクスチャの `P`、
意図的に逆順へ入れ替えた `AGE` / `FINGERPRINT`）。

**警告が出ること自体を検証している 8 件では `suppressWarnings()` を使っていない。**
前者は「警告を消す」だけだが、`expect_warning()` は「警告が出ることが正しい」という
検証になり、将来スクリーニングが壊れたときにテストが落ちる。
真陽性の警告を黙らせるのは、まさに §2 が警告している失敗様式である。

**訂正（#67）**: この節はもともと「`suppressWarnings()` は使っていない」と
書いていたが、**事実と違う**。`test-axis-screening.R` の 4 箇所
（L73 / L129 / L511 / L524）と `test-blocking.R` の複数箇所で使っている。
同じ文書の §3「影響」も「`expect_warning()` か `suppressWarnings()` が要る」と
書いており、**文書内で矛盾していた**。

使っているのは、**警告が検証対象ではない**テストである。L511 は同点処理が
乱数を引かないことを、L524 は screen あり・なしでスコアが一致することを
検証しており、そこで出る警告はどちらも検証対象の外側にある。区別の基準は
「警告が出ることがそのテストの主張か」であって、「警告を見たら黙らせてよいか」
ではない。

なお**守ろうとしていた保証は別のテストが守っている**。警告を出さなくする変異は
14 件、軸スクリーニングを無効化する変異は 31 件のテストで落ちる。
これは「文書の記述が実態と違う」問題であって、検証の穴ではなかった。

## 3. `lsh_candidates()` の `blocking` 属性が classed オブジェクトになり、取りこぼしで警告するようになった（Issue #36）

**対象**: `lsh_candidates()` の返り値に付く `attr(x, "blocking")`。

**変更前**: 素の `list`（`n_pairs_full`, `n_pairs_kept`, `kept_fraction`,
`n_anon_without_candidate`, `n_hash`, `bands`）。`print()` するとリストがそのまま出る。

**変更後**: `"reid_blocking"` クラスの list。既存フィールドは**すべてそのまま残る**ので
`attr(x, "blocking")$n_pairs_kept` などは従来どおり動くが、`print()` の見た目が変わり、
次のフィールドが増える。

- `method` — ブロッキング方式の名前
- `n_raw` / `n_anon`
- `reduction`（= `1 - kept_fraction`）
- **`n_true_pairs` / `n_true_pairs_kept` / `recall`**

さらに `recall < 1` のとき `warning()` を出すようになった。

### なぜ変えたか

`lsh_candidates()` は #18 の時点で「捨てた量」（`kept_fraction`,
`n_anon_without_candidate`）は記録していたが、**捨てたものの中に正解ペアが
何件あったか**は記録していなかった。この 2 つは違う。

README が推奨していた `bands = 32` の設定を実測すると、削減率 96.6% の裏で
**正解ペアの 11.5% を捨てていた**（recall 0.8850）。この数字は Issue #36 まで
誰も見ていない。再識別率だけが静かに下がる。`docs/lessons-learned.md` §2 そのものである。

### 数値は変わらない

同じ候補集合が返るので、`score_*()` 以降の数値は一切変わらない。
変わるのは `print(attr(x, "blocking"))` の表示と、警告が出るようになったことだけである。

### 影響

`recall < 1` のとき警告が出るため、`lsh_candidates()` をテスト内で呼んでいる箇所は
`expect_warning()` か `suppressWarnings()` が要る（`test-setsim.R` の 2 箇所を更新した。
取りこぼしそのものを検証しているケースは `expect_warning()`、
バンド数を振って挙動を比べているケースは `suppressWarnings()`）。

## 4. 同点判定に許容誤差 `tolerance` を導入した（Issue #61）

**対象**: `reid_evaluate()` / `reid_confidence()` / `match_greedy()` /
`match_optimal()` の新しい `tolerance` 引数、および内部の `reid_per_anon()`。

**変更前**: 同点判定は `==` による厳密比較（＝ `tolerance = 0` 相当）
**変更後**: 既定 `tolerance = sqrt(.Machine$double.eps)`（約 1.5e-8）の**相対**許容誤差

### なぜ変えたか

`score_num()` は `|raw - anon|` なので、厳密演算ではすべての値を `c > 0` 倍しても
全スコアが `c` 倍になるだけで、同点構造は不変である（尺度同変性）。
double ではこれが破れる:

```
42.3 - 41.2 = 1.0999999999999943
43.4 - 42.3 = 1.1000000000000014
```

実数としては等しいが double では 7.1e-15 違う。この差が `==` を通ると、
**同じデータを 1/10 単位で書き直しただけで同点が順序に変わる。**

実測（n=200、各 ANON に対称な第 3 者を 1 人ずつ仕込んだ構成。
`docs/adversarial/adv2-02-probe.R` §C3。真の RISK はどのレコードも厳密に 1/2）:

| | 整数単位 | 1/10 単位 |
|---|---|---|
| `success_analytic` | 0.494167 | **0.504167** |
| **`max_risk`** | **0.5000** | **1.0000** |
| `TIE_SIZE > 1` の件数 | 198 | **108** |
| `precision_recall` の行数 | 3 | **93** |

per-record の内訳は、厳密には RISK = 0.5 なのに **0 と報告 43 件（過小）/
1 と報告 47 件（過大）**。両方向に外れるので「安全側に倒れている」という
弁護は立たない。README が「平均だけを見ていると見落とす情報」として強調する
`max per-record risk` が 0.5 → 1.0 と反転すること、および #44 で既定を
`"margin"` にした根拠である PR 曲線の解像度が、この構成では
93 行中 90 行が ~1e-14 の丸め誤差から作られた偽の解像度であることが、
この指摘の重みである。

### どう直したか

同点判定のたびに `abs(a - b) < tol` を書くのではなく、**値の側を 1 回書き換える**。
1 つの ANON レコードの候補スコアのうち、互いに `tolerance` 以内のものを
その群の**最小値**に揃える（`snap_tied_values()`）。既存の `==` / `<` / `min()` は
そのまま厳密比較として動き、推移性と順序が保たれる
（pairwise な `abs(a - b) < tol` は推移的でない）。

群分けはソート後の隣接差に対する single-linkage で、
`tolerance * max(1, |a|, |b|)` より広い間隔が新しい群を作る。
`min()` が保存されるので **`BEST_SCORE` と勝者の同一性は動かない。**
動くのは「何件が勝者と同点か」だけである。

適用箇所:

- `reid_per_anon()` — `sum(v == best)` / `sum(v < true_score)` / `sum(v == true_score)`
- `reid_confidence()` — `TIE_SIZE`、`SECOND_SCORE`、`MARGIN`（`SD_SCORE` は
  「候補スコアの散らばり」であって同点判定ではないので生の値のまま）
- `match_greedy()` — `resolve_min_distance_ties()` に渡す前の DISTANCE と
  タイサイズの計算
- `match_optimal()` — **CONFIDENCE の同点カウントのみ。** 割当そのものは
  生のコストで解く。報告を単位不変にするためにソルバの入力を摂動させると
  「どの割当が最適か」が変わりうるので、この修正が主張している範囲を超える

### 何が変わり、何が変わらないか

**変わるもの** — 同点判定に丸め誤差が効いていたデータだけ:

`success_analytic` / `success_mean` / `max_risk` / `RISK` / `TIE_SIZE` /
`MARGIN` / `ECCENTRICITY` / `CONFIDENCE` / `precision_recall` / `top_k` /
`baseline` の mode。

**変わらないもの**:

- `BEST_SCORE` と、どの候補が勝つか（`snap_tied_values()` は `min()` を保存する）
- 整数値のスコア表、および候補スコアが 8 桁以上離れているデータの一切
- `SD_SCORE`

### 実測: 変更前後の比較

`tolerance = 0`（変更前）と既定（変更後）を同じフィクスチャで比較した。

| フィクスチャ | `analytic` 前/後 | `max_risk` 前/後 | PR 行数 前/後 | `TIE_SIZE>1` 前/後 |
|---|---|---|---|---|
| `V = 10,20,30,40,40,40` (n=6) | 0.666667 / 0.666667 | 1.0 / 1.0 | 4 / 4 | 3 / 3 |
| `V = 1,1,2,2,3,3` (n=6) | 0.500000 / 0.500000 | 0.5 / 0.5 | 1 / 1 | 6 / 6 |
| adv2 C3、整数単位 (n=200) | 0.494167 / 0.494167 | 0.5 / 0.5 | 3 / 3 | 198 / 198 |
| **adv2 C3、1/10 単位 (n=200)** | **0.504167 / 0.494167** | **1.0 / 0.5** | **93 / 3** | **108 / 198** |
| 連続値ノイズ sd 0.5 (n=150) | 0.833333 / 0.833333 | 1.0 / 1.0 | 150 / 150 | 0 / 0 |
| `create_dummy_qi_data` の AGE (n=200) | 0.113560 / 0.113560 | 1.0 / 1.0 | 7 / 7 | 185 / 185 |

**変わったのは丸め誤差が効いていた 1 行だけで、しかも整数単位の答えに一致した。**
README の全コード例（`docs/verify-readme-examples.R`）も、既存テストも、
1 件も数値が動かなかった。

`match_greedy(confidence = "tie")` を 1/10 単位の n=200 で見ると、
`CONFIDENCE == 1`（＝最良候補が一意）の件数が **92 → 2** に変わる。
198 件は本当は 2 者同点なので、2 件が正しい。

### 偽陽性の確認

許容誤差が大きすぎて本来別物の候補を同点扱いしないことを実測で確認した
（`tests/testthat/test-confidence.R`）:

- 相対 1e-7 離れた 4 値（既定許容誤差の 10 倍）→ 4 群のまま
- 相対 1e-12 離れた 2 値 → 1 群に融合
- `Inf` は有限値と融合しない（`Inf - Inf` が `NaN` になる経路を別扱いしている）

single-linkage なので原理的には連鎖しうる（互いに許容誤差以内の値の梯子が
端から端まで融合する）が、相対 1.5e-8 で 2 倍の幅を張るには
1 つの ANON レコードの候補が 10^8 件必要になる。

### 過去の数値を再現するには

`tolerance = 0` を明示的に渡す。`reid_evaluate()` /
`reid_confidence()` / `match_greedy()` / `match_optimal()` のいずれも受け付ける。

### 移行時に確認すべきこと

1. **スコアの有効数字が 8 桁を超えて意味を持つデータ** — 既定の相対許容誤差は
   double の 16 桁のうち下半分を捨てる（`all.equal()` の既定と同じ）。
   候補スコアの差がそれより小さいところに情報があるなら `tolerance` を下げる。
2. **`TIE_SIZE == 1` を「一意に特定できた」の意味で使っているコード** —
   丸め誤差由来の一意が消えるので、件数が増える方向にも減る方向にも動きうる。
3. **過去に出した報告書との比較** — 上表のとおり、整数スコアや
   十分に離れたスコアのデータでは数値は変わらない。変わったなら、
   その報告書の数値が単位の選び方に依存していたということである。

### 対象外

`top_k_candidates()` の `v <= kth`（`R/blocking.R`）には入れていない。
`ties = "keep"` は同点を切らずに残す設計なので、丸め誤差で「同点でない」と
判定されても候補を**多めに**残す方向にしか外れず、recall は下がらない。
`reid_by_*()` は `match_greedy()` を経由するので、自動的に対象に含まれる。

## 4b. `unicity_fraction()` / `unicity()` に `tolerance` が付いた（Issue #58 × #61）

**対象**: `unicity_fraction()` と `unicity()` の新しい `tolerance` 引数
（既定 `reid_tie_tolerance()`、上の 4 と同じ値）。

**変更前**: 複数列を `as.character()` して連結したキー。double は 15 桁で印字されるため
`0.1+0.2` と `0.3` が同一視され、逆に `"\r"` を含む文字列は別レコードを衝突させた。
**変更後**: 列ごとに同値クラスの整数コードへ直してから連結し、**double 列は
`snap_tied_values()` を通す**。

### なぜ両方の Issue を並べて記録するか

#58（キー衝突）と #61（同点の許容誤差）を**別々に直すと不変条件が壊れる**。
`R/unicity.R` の冒頭は unicity を「実際の攻撃の成功率の**下界**」と定義している。

| | unicity | 攻撃 (`reid_evaluate`) | 下界 |
|---|---|---|---|
| 修正前（master 3f6d2f0） | 0（印字で潰れる） | 1（厳密比較） | 成立 |
| #58 のみ | 1（厳密比較） | 1（厳密比較） | 成立 |
| #61 のみ | 0（印字で潰れる） | 0.5（許容誤差） | 成立 |
| **#58 + #61（許容誤差なし）** | **1** | **0.5** | **破綻** |
| #58 + #61（本節の対応） | 0 | 0.5 | 成立 |

フィクスチャは `c(0.1 + 0.2, 0.3)`。**どちらのブランチ単独でも成立していた性質が、
統合した瞬間に壊れる**という型の不具合なので、統合時に測って初めて見つかる。
`tolerance = 0` を両方に渡せば従来どおり厳密比較になり、そのときも下界は成立する。

### 2 つの層は同じ検査ではない（同じである必要もない）

許容誤差の当て先が違う。unicity は**値**に、スコア層は**値の差**に当てる。

| 入力 | unicity | 攻撃 |
|---|---|---|
| `c(0.1+0.2, 0.3)` | 0 | 0.5 |
| `c(1e15, 1e15+1)` | **0** | **1** |

後者では相対差 1e-15 なので unicity は同一値と見るが、攻撃が見る候補距離は 0 と 1 で
明確に別である。**unicity の方が常に粗い**（＝保守的）であればよく、それが下界の定義が
要求する唯一の向きである。この非対称を roxygen とテストの両方に書いた。

## 5. `combine_scores()` が尺度差で警告するようになった（Issue #57）

**対象**: `combine_scores()`。新しい引数 `scale_check = c("warn", "none")`（既定 `"warn"`）。

**変更前**: 警告なし。入力スコアの尺度が何桁違っても黙って足す。
**変更後**: 重みをかけた後の各成分の標準偏差の比が **10 倍** を超えると `warning()`。

### 返り値は変わらない

`combine_scores()` が返す SCORE 列は 1 ビットも変わらない。増えたのは警告だけである。
`scale_check = "none"` で従来どおり無言になる。

### なぜ入れたか — 「29 倍の過小報告」は条件付きだった

敵対的検証は「正規化しないと最大 29 倍の過小報告」と報告した。**この数字を一般則として
扱ってはいけない。** 実測すると、害が出るかどうかは**支配する軸が情報量を持つか**で決まり、
**両方向に振れる**。

フィクスチャ: `create_dummy_qi_data(people = 200, seed = 1)` の RAW を複製し、
ANON 側で AGE に ±2 のノイズ（`set.seed(42)`）、SPEND_DIST の各金額に
`rnorm(sd = 30)` のノイズ（`set.seed(43)`）を与えたもの。

| スコア | sd | 単独の success |
|---|---|---|
| `score_char("ZIP")` | 0.53 | 0.2000 |
| `score_num("AGE")` | 13.84 | 0.1127 |
| `score_dist("SPEND_DIST")` | 8769 | 0.0300 |

**害が出る側**（支配軸が最も情報量に乏しい SPEND_DIST）:

| 組み合わせ | success |
|---|---|
| ZIP 単独 | 0.2000 |
| ZIP + AGE（正規化なし） | 0.4303 |
| ZIP + AGE + SPEND_DIST（正規化なし） | **0.0300** |
| ZIP + AGE + SPEND_DIST（`range` 正規化） | **0.8750** |

0.0300 と 0.8750 の比が 29 倍である。**属性を 2 つ足したのに、ZIP 単独の 0.2000 を
下回る。** 警告もエラーも出ず、`axis_report()` は 3 軸すべてを informative と判定する
（軸スクリーニングは「情報量」を見るので「尺度」を原理的に検出できない）。

**害が出ない側**（支配軸が最も情報量の多い軸）: 下の較正表 A のとおり、情報量の多い軸が
支配する向きでは sd 比 100 倍でも成績は落ちない。

### 閾値 10 の較正

`combine_scores(list(a, b), weights = c(1, w))` の `w` を振って sd 比を変え、
`reid_evaluate(seeds = 1:2)$success_analytic` を実測した。

**A. AGE + ZIP**（左が AGE 支配、右が ZIP 支配。ZIP の方が情報量が多い）

| sd 比 | 100 | 30 | 10 | 3 | 1 | 3 | 10 | 30 | 100 |
|---|---|---|---|---|---|---|---|---|---|
| | ← AGE 支配 | | | | 均衡 | | | | ZIP 支配 → |
| success | 0.3750 | 0.3800 | 0.8417 | 0.8417 | 0.8417 | 0.8417 | 0.8417 | 0.8417 | 0.8417 |

**B. ZIP + SPEND_DIST**（右が SPEND_DIST 支配。SPEND_DIST は情報量に乏しい）

| sd 比 | 100 | 30 | 10 | 3 | 1 | 3 | 10 | 30 | 100 |
|---|---|---|---|---|---|---|---|---|---|
| | ← ZIP 支配 | | | | 均衡 | | | | SPEND_DIST 支配 → |
| success | 0.4450 | 0.4450 | 0.4450 | 0.4450 | 0.4450 | 0.4400 | 0.3900 | 0.2500 | 0.1350 |

B の損失は sd 比 3 まで 1% 未満、10 で −12%、30 で −44%、100 で −70%。
A は 10 までは損失ゼロで、30 で −55% に落ちる。
**10 は「目に見える損失が始まる点」であり、かつ A 側で偽陽性を出さない点**なので、
これを閾値にした。3 まで下げれば B の −12% も捕まえられるが、A の sd 比 10（損失ゼロ）に
発火するため、警告そのものが無視されるようになる。

判定は**重みをかけた後**の sd で行う。すでに `weights` で尺度差を補正した呼び出しを
警告しないためである（実測: `weights = c(1, sd(age)/sd(zip))` は正規化と同じ 0.8417 を出す）。
重み 0 の成分と SCORE が定数の成分は判定から除く。どちらも全候補に定数を足すだけで
順位を変えられないため、含めると比が `Inf` になって必ず発火する。

### README も直した（掲載値が過小だった）

README の統合層の実演は `combine_scores(list(s_age, s_zip))` と書かれており、
**同じページのパイプライン図（`normalize_scores() → combine_scores()`）と食い違っていた。**
掲載されていた `success rate 0.4303` はコードの出力としては正しいが、
**同じ攻撃者知識で正規化を挟めば 0.8417 になる。** 公開文書が実際のリスクを
半分以下に見せていたことになるので、実演コードを正規化ありに直し、
正規化を省いた場合の 0.4303 との対比を新しい節として明記した。

API 表の「正規化して加重和」という説明も実装と逆だったので直した。

これに伴い README の `#>` 出力が 6 か所変わった（`combined` を使う
`match_greedy()` / `reid_confidence()` の例を含む）。
`Rscript docs/verify-readme-examples.R` は 0 不一致・終了コード 0。

### 影響

意図的に尺度差を残している呼び出しは警告を明示的に扱う必要がある。

| 箇所 | 対応 |
|---|---|
| `R/idf.R` の `score_idf_match()` | `scale_check = "none"`。IDF ブロックでは尺度そのものが証拠（まれな値の列が普通の列より重いのは仕様） |

`score_multi()` の既定 `normalize = "range"` では警告は出ない。

## 6. `score_mahalanobis()` が悪条件の共分散で警告するようになった（Issue #59）

**対象**: `score_mahalanobis()` と `score_multi(method = "mahalanobis")`、および
`score_multi()` / `score_by_knowledge()` の統合結果全般。

**変更前**: 特異で反転できないときだけエラー。可逆だが悪条件なら無言。
**変更後**: 共分散（ridge 適用後）の**条件数が 100 を超えると警告**。あわせて、
**統合結果が単一軸の最良値を下回ったときにも警告**する。

### 返り値は変わらない

SCORE 列は変わらない。既定値（`ridge = 1e-6`, `cov_from = "raw"`）も変えていない。
増えたのは警告だけである。

### 再現 — 報告は再現した

`docs/adversarial/p08-mahalanobis.R` を実行し、報告どおりの値が出た。

| eps_sd | noise | cor(A,B) | `weighted` | `mahalanobis` | 比 |
|---|---|---|---|---|---|
| 0.5 | 1.0 | 0.9998 | 0.6250 | 0.0500 | 12.50x |
| 0.5 | 2.0 | 0.9998 | 0.3450 | 0.0200 | **17.25x** |
| 3.0 | 2.0 | 0.9922 | 0.3800 | 0.1150 | 3.30x |
| 30.0 | 2.0 | 0.6459 | 0.6750 | 0.6200 | 1.09x |

`score_mahalanobis(A, B)` = 0.0250 は `score_num(A)` 単独の 0.0500 を下回る。
警告は出ず、`axis_report()` は 3 軸すべてを informative と判定する。

### ただし「相関が強いと壊れる」ではない — **決めているのは加工ノイズの形**

相関だけを動かした掃引では説明がつかなかったので、**加工ノイズの形**を分けて測った。
A と B の相関 rho、C は独立、`success_analytic`（200 レコード）。

**A. 等方ノイズ**（各列に同じ sd。p08 が使っている形）

| rho | κ(S) | `weighted` | `mahalanobis` | 損失 |
|---|---|---|---|---|
| 0.000 | 3.2 | 0.9900 | 0.9950 | 0.99x |
| 0.600 | 6.6 | 0.9850 | 0.9500 | 1.04x |
| 0.900 | 26.7 | 0.9600 | 0.9200 | 1.04x |
| 0.950 | 54.0 | 0.9400 | 0.8750 | 1.07x |
| 0.980 | 136.1 | 0.9450 | 0.7100 | 1.33x |
| 0.990 | 273.4 | 0.9350 | 0.5600 | 1.67x |
| 0.999 | 2755.6 | 0.8850 | 0.2100 | **4.21x** |

**B. 母集団の共分散に沿ったノイズ**（`delta ~ N(0, c^2 S)`）

| rho | κ(S) | `weighted` | `mahalanobis` | 利得 |
|---|---|---|---|---|
| 0.000 | 3.2 | 0.9850 | 0.9800 | 0.99x |
| 0.900 | 26.7 | 0.9550 | 0.9800 | 1.03x |
| 0.990 | 273.4 | 0.8900 | 0.9800 | 1.10x |
| 0.999 | 2755.6 | 0.8400 | 0.9800 | **1.17x** |

**同じ共分散・同じ条件数で結論が逆**である。しかも相関が強いほど、A では悪化が、
B では改善が大きくなる。したがって:

- **条件数は「壊れやすさ」を示すだけで、どちらに転ぶかは決めない。** 警告文も
  そう書いてある（両方向の実測値を併記）
- リポジトリ内の既存テスト
  「on correlated attributes Mahalanobis beats the plain weighted sum」の
  フィクスチャ `redundant_join()` は、加工ノイズを潜在変数に沿って与えている
  （`A + shift`, `B + 3 * shift`）。つまり **B の形**であり、κ は 1400〜3100 で
  新しい警告が出るが、**Mahalanobis が勝つ**。この事実自体をテストに固定した
  （"the #59 condition-number warning marks fragility, not a wrong answer"）

閾値 100 は A の表による。κ 54 までは損失 7% 以下、136 で 1.33 倍、273 で 1.67 倍。

### 検討したうえで維持した既定 — `ridge = 1e-6`

「既定 `ridge = 1e-6` が最悪」という報告は数値としては正しいが、**上げるのは対策に
ならない**。κ = 2756 の 2 つの regime で `ridge` を振った実測:

| ridge | A: 等方（悪い側） | B: 共分散に沿う（良い側） |
|---|---|---|
| 1e-6 | 0.2100 | 0.9800 |
| 1e-2 | 0.5150 | 0.9550 |
| 1e-1 | 0.8150 | 0.9150 |
| 1 | 0.8950 | 0.8650 |
| 10 | 0.9100 | 0.8550 |
| （`weighted`） | 0.8850 | 0.8400 |

`ridge = 1` で**両方とも加重和の値に収束する**。つまり大きな ridge は
「Mahalanobis をやめて加重和に戻す」ことと同じで、悪い側を救う代わりに良い側の
利得（0.9800 → 0.8650）を捨てる。**フィクスチャ依存の失敗を、無条件の失敗と
交換することになる**ので既定は変えない。roxygen にこの表の要点を書いた。

### 検討したうえで維持した既定 — `cov_from = "raw"`

| cov_from | A: 等方（悪い側） | B: 共分散に沿う（良い側） |
|---|---|---|
| raw | 0.2100 | 0.9800 |
| anon | 0.3350 | 0.9800 |
| pooled | 0.2650 | 0.9800 |

`"anon"` は悪い側をいくらか救い、良い側を損なわない（p08 のフィクスチャでも
raw 0.0250 / anon 0.1850 / pooled 0.1750）。それでも既定は `"raw"` のまま置く。

- 0.3350 は `weighted` の 0.8850 に遠く及ばず、**救済にはなっていない**。
  「既定を変えたので大丈夫」という誤った安心を与える方が有害である
- `cov_from` は**脅威モデルの選択**であって調整つまみではない。攻撃者は自分が
  持っている母集団で白色化する。既定を「加工後データの共分散」にするのは、
  攻撃者が加工後の分布を知っている前提を黙って足すことになる

roxygen には診断手段として `"anon"` を挙げ、実測値も書いた。

### 統合結果が単一軸を下回ったときの警告

「2 列使ったのに 1 列より安全」は論理的に破綻した結果なので、
`score_multi()` / `score_by_knowledge()` が統合結果を最良の単一軸と比べ、
下回っていれば警告する。

**#35 の軸スクリーニングが何も検出しなかったときだけ発火する。** 無情報な軸が
原因のケースは #35 が同じ助言つきで既に報告しており、別の言い回しで二度言うと
どちらも読み飛ばされるようになる。この検査が埋めるのは #35 が原理的に見えない穴、
すなわち**各列は単独で情報を持つのに統合すると下がる**ケースである。

### 影響

| 箇所 | 対応 |
|---|---|
| `test-multiattr.R`（悪条件フィクスチャ 4 テスト） | `suppressWarnings()`。不変性・`ridge`・`cov_from` の検証であって条件数の検証ではない |
| `test-multiattr.R` / `test-knowledge.R`（W < M < S 系 3 テスト） | `suppressWarnings()`。FINGERPRINT 単独が全件識別するため S 水準の等重み統合が単一軸を下回る。真陽性だがテストの主題は水準の順序 |
