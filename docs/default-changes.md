# 既定値の変更履歴

このパッケージは安全性評価ツールなので、**同じコードに同じデータを与えて過去と違う数値が出る**変更は、
それが意図的なものであっても記録に残す。ここはその記録である。

「壊れていたものを直した」変更はここには書かない。**意図的に既定を変えた**ものだけを書く。

---

## 1. `confidence` の既定を `"tie"` → `"margin"`（Issue #44）

**対象**: `match_greedy()`, `match_optimal()`, `reid_evaluate()`, `reid_per_anon()` の
`confidence` 引数、および `reid_confidence()` の `method` 引数。

**変更前**: `"tie"`（= `1 / 同点候補数`）
**変更後**: `"margin"`（= eccentricity `(2位のスコア − 1位のスコア) / sd(候補スコア)`）

### なぜ変えたか

#12 で「攻撃者は全件を当てにいかない。一部を高精度で特定する方が深刻」という前提を置いた。
それを測るのが `reid_evaluate()` の精度–再現率(PR)曲線である。

ところが `"tie"` は**連続スコアでは解像度がない**。最良候補が一意な記録はすべて 1 になるため、
連続スコアではほぼ全件が 1 に潰れ、PR 曲線の閾値が 1 点しか取れない。
1 点しか取れない PR 曲線は、全体成功率をもう一度書いているだけで、
「リスクの形」を見せるという指標本来の目的を果たさない。

`"margin"` は確率ではないが**順序**であり、閾値スイープが必要とするのは順序である。

### 何が変わり、何が変わらないか

**変わるもの** — `CONFIDENCE` 列と、それを閾値に使うすべて:

- `match_greedy()` / `match_optimal()` の `CONFIDENCE` 列
- `reid_evaluate()` の `precision_recall` 表と `per_record$CONFIDENCE`
- `min_confidence` の意味するスケール
- `reid_confidence()` の `CONFIDENCE` 列（`TIE_SIZE` / `MARGIN` / `SD_SCORE` /
  `ECCENTRICITY` はどちらの設定でも同じ値が入る）

**変わらないもの** — リスクそのもの:

- 割り当て結果（`RAW_ROW_NUMBER`）と `RESULT`
- `success_analytic` / `success_mean` / `success_sd` / `baseline` / `lift`
- `top_k` / `per_record$RISK` / `max_risk`

信頼度は記録を**並べ替える**だけで、リスクを変えない。これは
`test-confidence.R` と `test-evaluate.R` でアサートしてある。

### 実測: 変更前後の比較

`seeds = 1:20` で測定。「変更前」は `confidence = "tie"`、「変更後」は `confidence = "margin"`。

#### `match_greedy()` の `CONFIDENCE`

| フィクスチャ | 変更前 (tie) 最小/中央/最大 | 相異なる値の数 | 変更後 (margin) 最小/中央/最大 | 相異なる値の数 |
|---|---|---|---|---|
| `V = 10,20,30,40,40,40` (n=6) | 0.3333 / 0.6667 / 1.0000 | 2 | 0.0000 / 0.3953 / 1.5811 | 4 |
| `V = 1,1,2,2,3,3` (n=6, 全件同点) | 0.5000 / 0.5000 / 0.5000 | 1 | 0.0000 / 0.0000 / 0.0000 | 1 |
| `V = 10..50` (n=5, 全件一意) | 1.0000 / 1.0000 / 1.0000 | 1 | 0.6325 / 0.8771 / 1.1952 | 3 |
| 連続値 n=150（ノイズ 0.5） | 1.0000 / 1.0000 / 1.0000 | **1** | 0.0001 / 0.0087 / 0.3941 | **150** |

#### `reid_evaluate()` の精度–再現率表

| フィクスチャ | | PR 表の行数 | 最上位行: 閾値 / 攻撃件数 / precision / recall |
|---|---|---|---|
| `V = 10,20,30,40,40,40` (n=6) | 変更前 | 2 | 1.0000 / 3 of 6 / 1.0000 / 0.5000 |
| | 変更後 | **4** | 1.5811 / **1 of 6** / 1.0000 / 0.1667 |
| `V = 1,1,2,2,3,3` (n=6) | 変更前 | 1 | 0.5000 / 6 of 6 / 0.5000 / 0.5000 |
| | 変更後 | 1 | 0.0000 / 6 of 6 / 0.5000 / 0.5000 |
| `V = 10..50` (n=5) | 変更前 | 1 | 1.0000 / 5 of 5 / 1.0000 / 1.0000 |
| | 変更後 | **3** | 1.1952 / **1 of 5** / 1.0000 / 0.2000 |
| n=12（同点あり） | 変更前 | 3 | 1.0000 / 5 of 12 / 1.0000 / 0.4167 |
| | 変更後 | **5** | 0.8228 / **1 of 12** / 1.0000 / 0.0833 |
| 連続値 n=150 | 変更前 | **1** | 1.0000 / 150 of 150 / **0.2467** / 0.2467 |
| | 変更後 | **150** | 0.3941 / **1 of 150** / **1.0000** / 0.0067 |

いずれも `success_analytic` は変わらない（順に 0.6667 / 0.5000 / 1.0000 / 0.6667 / 0.2467）。

最後の行がこの変更の要点である。連続スコア n=150 で、変更前の PR 曲線は
**1 行しかなく、precision は全体成功率 0.2467 そのもの**だった。
変更後は 150 行になり、最も自信のある 1 件だけを攻撃すれば precision 1.0000 であることが見える。
リスクは同じで、見え方だけが変わった。

### 過去の数値を再現するには

`confidence = "tie"`（`reid_confidence()` では `method = "tie"`）を明示的に渡す。
`"tie"` は削除していない。

### 移行時に確認すべきこと

1. **`CONFIDENCE` をリテラルと比較しているコード** — `CONFIDENCE == 1` は
   `"tie"` では「最良候補が一意」を意味したが、`"margin"` では何も意味しない。
2. **`min_confidence` に定数を渡しているコード** — スケールが違う。次項を参照。
3. **過去に出した報告書との比較** — `success_analytic` などのリスク量は比較できる。
   PR 表と `CONFIDENCE` は比較できない。

### 併せて重要: eccentricity にはスケールの可搬性がない

これは既定を変えたこと自体より重要かもしれない。

eccentricity は**その記録自身の候補スコアの散らばり**に対する比なので、
数値の範囲はスコア表の性質で決まり、リスクの大きさでは決まらない。

| スコア表 | eccentricity の最大値 |
|---|---|
| 密な 150 人 2 属性の数値フィクスチャ | **0.45** |
| 疎なトランザクション的スコア（#23） | **4.86** |

一桁違う。しかも密な方は 98% が再識別された条件である。したがって:

- **閾値はデータセット間で使い回せない。** `min_confidence = 0.3` は、
  あるスコア表では上位 1 割を攻撃し、別のスコア表では全件を攻撃する。
- **Narayanan & Shmatikov の φ = 1.5 は移植できない。** 疎データ向けの値であり、
  密データでは全件を棄却して 0 を返す。
  「閾値が違うスケールだったので 0 件」と「本当に安全なので 0 件」は
  出力上区別がつかない（`docs/lessons-learned.md` §2）。
  `match_greedy()` / `match_optimal()` は全件棄却時に警告するが、
  それは最後の砦であって、閾値を選ぶ作業の代わりにはならない。
- **2 つの eccentricity を比べてよいのは同一スコア表の中だけ。**
  「A は 0.9 まで出たが B は 0.4 だから A の方が危険」は読み取れない。
  データセット間の比較には `reid_evaluate()` の `success_analytic` や
  `max_risk` を使う。これらは信頼度の選択に影響されない。

閾値は必ず実測分布から取る:

```r
stats::quantile(reid_confidence(scores, "margin")$CONFIDENCE, 0.9)
```

`"tie"` にはこの問題がない（`(0, 1]` の確率で、どこでも同じ意味を持つ）。
それが解像度をほぼ完全に失うことの代償である。

### テスト側の対応

既定変更で落ちたアサーションは **19 件（6 ファイル・10 テスト）**。
Issue #44 本文の見積もりは 3 箇所だったが、実測はその 6 倍以上だった。内訳:

| ファイル | 落ちたアサーション | 落ちたテスト |
|---|---|---|
| `test-layers.R` | 5 | 3 |
| `test-evaluate.R` | 7 | 1 |
| `test-confidence.R` | 3 | 2 |
| `test-generalize.R` | 2 | 2 |
| `test-assignment.R` | 1 | 1 |
| `test-setsim.R` | 1 | 1 |

見積もりが外れた理由は、`match_greedy()` の `CONFIDENCE` を
`1/k` としてアサートしている箇所が、信頼度そのものを扱うテストファイル以外
（集合類似度・一般化・レイヤ結合）にも散らばっていたため。
`docs/lessons-learned.md` §1「コードを読んだだけの指摘は、起票前に実行して確かめる」の
再現である。方針は次のとおり:

- **`1/k` の算術そのものを検証しているテスト**は `confidence = "tie"` を明示的に渡し、
  書かれたときの意図を保つ（`test-layers.R`, `test-assignment.R`,
  `test-generalize.R`, `test-setsim.R`, `test-evaluate.R` の tie 版）
- **既定そのものを検証していたテスト**は意図を反転させて書き直す
  （`test-confidence.R` の "match_greedy() defaults are unchanged by the new
  arguments" → "the confidence default is 'margin' (#44)"）
- **新しい既定の数値を固定する**テストを追加する
  （`test-evaluate.R` の "the default sweep ('margin', #44) refines the tie
  sweep rather than replacing it"）

`confidence = "tie"` を足しただけの箇所も、なぜ足したのかをコメントで残してある。
黙って引数が増えていると、次に読む人には「元からそう書かれていた」ようにしか見えないため。
